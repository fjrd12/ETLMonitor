IDoc Error ETL — Architecture Proposal

Note: sample source files for this project contained real SAP usernames, system IDs, and business data. Replace any such identifiers with placeholders before sharing this document externally, per data-handling policy.

Guiding idea: build the toy demo as a pipeline of pure functions over folders, with every storage touchpoint hidden behind a small interface. That's what lets you swap "local folder + SQLite" for "Dataverse + central log" later without rewriting the ETL logic — you only write a new adapter.

2. Layering

  • Landing zone — anything dropped in the data lake root: {DOCNUM}_CTRL.json, {DOCNUM}_STAT.json, {DOCNUM}_CONTENT.xml.
  • ETL 1 (route & land) — reads SNDPRN/RCVPRN from CTRL.CONTROL to determine the server, creates SERVER/{input,output,DW} if missing, creates SERVER/input/{GLOBAL_UUID}/ if missing, moves the triplet there, deletes from origin.
  • ETL 2 (monetize) — for each UUID folder in input, looks up MESTYP in monetizer.json, resolves the matching .xslt, transforms CONTENT.xml, moves source files to output.
  • ETL 3 (warehouse) — ORM layer (SQLAlchemy) creates the SQLite schema on first run, upserts into ErrorEvents, Event_Meta, Event_meta_field, Messages, and read-time aggregate views.
  • Presentation — a deterministic static HTML generator (Jinja2) reads the SQLite tables and renders the dashboard + drill-down pages.

3. Key design decisions

Storage abstraction

This is the piece that buys you Dataverse later. Define one small interface:

class EventSink(ABC):
    def upsert_event(self, event: ErrorEvent) -> None: ...
    def upsert_messages(self, event_uuid: str, messages: list[Message]) -> None: ...
    def upsert_meta(self, event_uuid: str, meta: list[MetaField]) -> None: ...

Today you implement SqliteEventSink. Later you add DataverseEventSink (Dataverse Web API) or CentralLogSink (event hub / REST endpoint). ETL 3 only ever talks to EventSink — nothing else in the pipeline changes.

Monetization as strategy pattern

monetizer.json is effectively a dispatch table {MESTYP: xslt_path}. Wrap it in a Monetizer class with a .transform(mestyp, xml_bytes) method (using lxml / saxonche for XSLT). New message types just mean a new .xslt + a JSON entry — no code change.

Schema validation on ingest

Define pydantic models for CtrlRecord and StatRecord once, and let ETL 1 fail loud-and-clear on malformed input rather than silently propagating bad data downstream.

Deterministic dashboard

Stable sort order (e.g. by DOCNUM or timestamp), no wall-clock-dependent content baked into IDs, templates rendered from DB state alone — so re-running the generator on the same DB always produces byte-identical HTML.

    etl2_monetize.py

    models.py             # pydantic + ORM models
  orchestrate.py           # runs 1 -> 2 -> 3 -> dashboard, toy-demo CLI

5. Data warehouse refinement

  • Make the four "Aggregates" (monthly, by system, by error type, cost) SQL views, not physical tables — keeps the SQLite demo simpler and always in sync.
  • Cost of the error needs a rule to populate Amount/Currency on ErrorEvents — likely a lookup table mapping (MESTYP, STATUS) → estimated cost/severity, since the raw IDoc doesn't carry a cost field itself.

6. Dashboard / drill-down

  • Landing page: table of ErrorEvents (sortable by date, system, type, module, status), plus small summary charts.
  • Each row links to a static event_detail_{uuid}.html page rendered from Event_Meta + Messages + the raw CONTENT.xml — all pre-generated, no server needed.
